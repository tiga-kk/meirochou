# 実装完了とレビュー依頼のプロトコル

この文書は、対象Taskを実装したエージェントがレビュー依頼を出す前に満たす共通の完了条件と、レビュー担当へ渡す依頼文を定める。Task固有の完了条件、対象ファイル、データ契約は各 `docs/plans/phase-*.md` を正とする。

## 1. 実装開始前

実装者はコードを変更する前に、次を短く記録する。

1. 対象Phase / Taskと、その完了条件。Phase 3/4ではPhase概要だけでなくリンク先のTask別実行計画を明記する。
2. 今回変更するファイルと、変更しない境界。特に後続Task、別Phase、未承認差分、公開境界、実地図を含めないことを明記する。
3. 参照した設計契約と既存テスト。

計画・契約・実装に矛盾がある場合は、実装を始めずに計画または進捗文書を訂正して理由を報告する。

## 2. テスト設計と実装順序

各振る舞いは、可能な限り失敗テストから始める。

1. 利用者または呼び出し元から見える期待結果をテスト名にする。内部実装の名前や手順をテストの主題にしない。
2. 対象Taskの境界で、正常系だけでなく不正入力、通信失敗、保存失敗、二重実行、期限切れ、競合・stale状態を必要に応じて扱う。
3. 失敗時に既存のLocalStorage state、購入状態、outbox、画面状態を壊さないことをテストする。
4. 純粋な変換・差分・パーサー・状態遷移はVitestで検証する。実際のモバイル操作、DOM、地図、設定、同期導線だけをPlaywrightで検証する。
5. バグ修正では、修正前に再現する回帰テストを追加する。

REDを確認してから最小限の実装でGREENにし、必要なリファクタリング後に関連テストを再実行する。実装都合だけのsnapshot更新で振る舞いの変更を隠してはならない。

## 3. レビュー依頼前の検証

対象Taskに書かれた検証を優先し、少なくとも以下を実行する。失敗・未実行の項目がある場合は、理由と影響を依頼に明記する。`npx biome check` は警告を含めてゼロ終了でなければレビュー依頼・コミットのブロッカーである。

### 常に実行する

```bash
npm run test:webapp
npm run check:webapp
npm run build:webapp
npm run verify:webapp:build
npx biome check
git diff --check
git status --short --branch
```

### 変更内容に応じて追加する

| 変更内容 | 追加検証 |
|---|---|
| 地図、設定、購入・保留、同期、主要モバイル操作 | `npm run test:e2e` |
| 公開対象、配信アセット、GASソース | `npm run verify` と公開境界監査（該当する `audit-public-tree` を実行） |
| 対象Phaseが定めるGAS契約 | `npm run verify:gas` と該当するcontract test |

localhost listenがsandboxで拒否される場合だけ、同じE2Eコマンドをsandbox外で再実行して判定する。テスト対象外のUI変更は、対象端末幅で手動確認した内容も記録する。

## 4. レビュー依頼に添える証跡

レビュー依頼には、必ず次を含める。

1. 対象Phase / Task、目的、変更しない境界。
2. 未コミット差分の対象範囲。別Taskの既存ステージ・未ステージ差分を含めないこと。
3. 実行した検証コマンドと、成功・失敗・未実行の結果。
4. 既知の未解決事項、リスク、スコープ外事項。

レビュー承認はコミット承認ではない。`comipath-web` では、対象ファイルだけをstageした差分、検証結果、提案コミットメッセージを提示し、ユーザーの明示承認後にだけcommitする。

## 5. コピペ用: 変更しない差分レビュー依頼

以下をそのままレビュー担当へ渡す。`<Phase>` と `<Task>` だけを対象に置き換える。

```text
AGENTS.md、docs/README.md、対象Phase/Taskの計画書を読んでください。
未コミット差分だけをレビューしてください。ファイルは変更しないでください。

対象: Phase <Phase> Task <Task>

確認項目:
- 計画・データ契約・公開境界との整合
- 仕様外のGAS通信、状態破壊、競合・stale問題
- テスト漏れと検証コマンドの妥当性
- TypeScript strict、Biome、既存UI回帰
- セキュリティ・公開情報混入

指摘は P0〜P3、根拠ファイル、修正方針で列挙してください。
問題がなければ「指摘なし」と、確認した範囲・残るリスクを書いてください。
```

レビュー担当は、レビュー対象外の既存差分を変更・stage・unstage・破棄・commitしてはならない。
